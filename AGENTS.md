# AGENTS.md — stcksmsh.github.io

Working notes for future agent sessions on this repo. State/context, not spec.

## Architecture

Astro (static output, MPA) + React islands, deployed to GitHub Pages. `src/layouts/Base.astro` is the shared layout: mounts `SintezaBackground` (the persistent `sinteza-viz` WebGL canvas, site-wide fixed background) and `GlobalPlayer` (persistent bottom audio bar) once, both `transition:persist`'d so they survive Astro's View Transitions client-side navigation. Content is federated at build time from each project's own `io-page` git branch (`scripts/federate.ts`, driven by `projects.manifest.json`) — `src/content/projects/` and `src/content/devlogs/` are gitignored, regenerated on every build.

**6 real pages**: `/` (home, teasers), `/projects`, `/projects/[slug]`, `/music`, `/devlog`, `/cv`. Each currently duplicates its own nav/card CSS in a page-scoped `<style>` block (a known wart, not yet worth the risk of consolidating).

## The visualizer integration (`sinteza-viz` / `stcksmsh/hysteresis`)

SoundCloud is embedded via iframe (cross-origin, no live audio access), so the visualizer runs entirely in **position-only mode**: `GlobalPlayer` dispatches `player:transport` window events (`trackchange`/`position`/`play`/`pause`), which `sinteza-viz`'s own internal listener consumes directly (not through `SintezaBackground` — that island only handles `setAccent` on trackchange, see its own comment). A track's `sidecar` content field (schema-2 JSON, generated via `sinteza-viz`'s `scripts/analyze.ts` from the original WAV) is what actually drives real visual sync; without it the visualizer just runs its own context-free idle autopilot regardless of what's playing.

**All 5 real tracks now have real sidecars** (as of this session): SIGSEGV, 0xC000021A, Hysteresis, Sampling Drift, Triple Pendulum — published under `public/sidecars/*.sidecar.json`, referenced by each `src/content/music/*.json`'s `sidecar` field. To add a new track: get its sidecar generated in the `hysteresis` repo (needs the original WAV — ask the user, they have the masters), copy the output JSON to `public/sidecars/<slug>.sidecar.json`, add a content entry with `sidecar: "/sidecars/<slug>.sidecar.json"` and `embedId: "stcksmsh/<lowercase-slug>"` (SoundCloud permalink pattern, confirmed).

**GlobalPlayer** (`src/components/islands/GlobalPlayer.tsx`) was rebuilt this session: real seek bar (drag-to-seek via debounced `onChange`, works for mouse/touch/keyboard), looping queue (`FINISH` wraps `(index+1) % tracks.length` instead of stopping dead), a queue-toggle panel. The old oscilloscope canvas is gone — it depended on a legacy per-track `envelope` field and did nothing for tracks without one. It also listens for `player:request-duck` (`src/lib/player-bus.ts`'s `onDuckRequest`) and steps the SoundCloud Widget API's `setVolume()` down/back (`rampVolume`, no native ramp primitive there, so a small stepped approximation of a fade) — any custom project page can duck the global player while it plays its own audio by dispatching that same window `CustomEvent`, see "Custom project pages" below.

**Seek bar duration bug (fixed)**: the first version above reported working in this sandbox but was actually broken in real use — end time never showed and the seek bar stayed disabled after the very first play. Root cause: `durationMs` was reset to 0 on every `playTrack()`/`widget.load()` call, and only ever repopulated by a `SC.Widget.Events.READY` listener bound *once* at mount — `READY` is not guaranteed to refire on a later `load()`. Fixed by fetching duration via `load()`'s own `callback` option (the reliable per-track-switch hook) with a `PLAY`-event fallback and a short retry loop (`getDuration()` can return `0` for a moment right after a sound becomes ready). **Lesson**: this sandbox cannot exercise the live SoundCloud widget at all (network-blocked), so anything gated on a specific widget event firing in a specific order needs to be reasoned through defensively (multiple redundant hooks) rather than assumed correct from a clean build/typecheck alone — a build passing here is not evidence the widget integration actually works.

**⚠️ `package-lock.json` pins a resolved commit SHA for the `sinteza-viz` dependency, not just the branch.** `package.json` tracks `github:stcksmsh/hysteresis#master`, but merging a fix to that repo's `master` does **not** automatically reach this site — the lockfile needs to be re-resolved separately: `npm install sinteza-viz@github:stcksmsh/hysteresis#master`, then commit the resulting `package-lock.json` diff. Landed fixes in `hysteresis` this session (flash pacing, real energy driving the visual, resize-debounce fixing a scroll-triggered stutter, onset particle removal) each needed this as a separate follow-up PR — don't assume a merged upstream fix is live without checking/doing this.

## Custom project pages (`page/` bundle contract)

By default every project on `/projects/[slug]` gets the same generic template (hero + stack ticker + devlog stream) built from just `meta.json`. A project can instead ship a genuinely custom hero — real interactive React/WebGL/Web Audio code it owns, not something hand-authored in this site repo — by adding an optional `page/` directory to its `io-page` branch, sibling to `meta.json`/`devlogs/`:

- `page/entry.tsx` — **required** to opt in. Default-exports a component with signature `({ project, devlogs }) => JSX`, where `project` mirrors the project's own `meta.json` and `devlogs` is a plain summary array (`{ id, title, date, tags }` — no rendered body; the devlog stream itself always stays this site's own generic, server-rendered section below the hero, for every project, custom or not).
- Any other code file (`.tsx`/`.ts`/`.jsx`/`.js`/`.css`) anywhere under `page/` — imported normally from `entry.tsx` (or from each other), mirrored into the site's own `src/generated/projects/<slug>/` and compiled by the site's own Vite build.
- `page/assets/**` (or any non-code file under `page/`) — mirrored as-is into `public/generated/projects/<slug>/`, fetch it at runtime via `/generated/projects/<slug>/<path>` (**not** an ES import — these are served as plain static files, not bundled).

`scripts/federate.ts` does the mirroring (`federateCustomPage()`), driven by GitHub's recursive git-trees API (needs `api.github.com`, same sandbox caveat as `listDevlogs` below). `src/pages/projects/[slug].astro` picks up `page/entry.tsx` via `import.meta.glob("../../generated/projects/*/entry.tsx")` and, if present for that slug, swaps in a `<div id="project-custom-root">` in place of the standard `<header class="project-hero">` — everything else (nav, devlog stream) stays the generic template.

**Why manual mounting, not `client:*`**: Astro's `client:load`/`client:only` directives need a *static* import in the `.astro` file's own frontmatter to generate a hydration entry point — a component reference pulled from `import.meta.glob` at runtime doesn't qualify and fails the build with `[NoMatchingImport]`. `[slug].astro` instead renders an empty root div server-side and mounts it by hand in a plain `<script>` (unconditional in the markup — Astro can only hoist/bundle a `<script>` it finds via static template analysis, so wrapping it in `{hasCustomPage && ...}` silently leaves it as *unprocessed inline text*, raw TS syntax and all, instead of compiling it; learned the hard way, see git history) that does its own lazy `import.meta.glob` + `ReactDOM.createRoot`.

**A federated `page/` bundle can't import this site's own internals** (`src/lib/*`, other components) — it's compiled as part of this build, but the project repo doesn't know this site's file layout and shouldn't depend on it. Anything a custom page needs from the site (e.g. `GlobalPlayer` ducking) goes through a `window` `CustomEvent` convention instead, matching how `sinteza-viz`'s own `player:transport` bus already crosses the repo boundary — see `src/lib/player-bus.ts`'s `requestDuck`/`onDuckRequest`. Small generic utilities (a scope-drawing hook, a ticker-padding helper) get a small duplicated copy in the project's own `page/` bundle rather than a relative import reaching into this repo — see `mouthpiece`'s `page/useScopeDraw.ts` for the pattern.

**Mouthpiece** (`stcksmsh/mouthpiece`) is the first (and so far only) project using this. Its `page/` bundle: `entry.tsx` (hero + "how it works" explainer) + `DemoScope.tsx` (the interactive word-reassembly demo, real Web Audio decode of real corpus clips) + `useScopeDraw.ts` + `style.css`, with `page/assets/manifest.json` + `page/assets/clips/*.opus` (curated speech fragments + provenance). This used to be a bespoke `src/pages/projects/mouthpiece.astro` + `MouthpieceDemoScope.tsx` living entirely in *this* repo (Astro's file-based routing naturally lets a static route shadow the dynamic `[slug].astro`, which is simpler when a component doesn't need to cross a repo boundary) — migrated onto the generic `page/` contract so Mouthpiece's own repo genuinely owns its page, not this one. If a future one-off custom page doesn't need real repo ownership (e.g. a demo whose only content is this site's own data), a bespoke shadowing `.astro` file is still a legitimate, simpler alternative — the two approaches aren't mutually exclusive, pick based on who should own the code.

## Design system notes

- `--bg-glass`/`--glass-blur` (glass-card treatment) + `--radius-panel`/`--panel-highlight`/`--panel-shadow` (soft-edged panel look) are the established visual language for anything sitting on top of the persistent visualizer background — nav, cards, the CV scrim, the player bar. Avoid flat opaque boxes or hard 1px borders against the canvas; they read as "old-style divs pasted on top" (a real complaint, fixed several times this session — always check new UI against this).
- `.coord` (section eyebrows, footer text, etc.) has a `text-shadow` specifically because a lot of these sit directly on the raw unscrimmed canvas outside any glass card — don't remove it without checking contrast there.
- `.ticker-viewport`/`.ticker-gap` (`global.css`) + `src/lib/ticker.ts`'s `padForTicker()` is the shared "newsreel" scrolling-chip mechanism, used by every `.stack` (tech tags) and `.tags` (devlog tags) list. `padForTicker` pads+gap-marks a short list so the `translateX(-50%)` loop never shows a blank gap or an unbroken run-on repeat. Deliberately *not* applied to the CV page's `.chips` (skills/certifications) — that page is a printable resume and a scroll animation would cut off content in print.
- **View Transitions + `transition:persist` gotcha**: even though a persisted element's DOM node/React state genuinely survives navigation (verified exhaustively — mount-count probing across link clicks and browser back/forward, on the actual production build), the browser's default View Transition crossfade still runs an opacity/`mix-blend-mode` animation on that element's own `::view-transition-old/new` pseudo-elements. Harmless for a `<canvas>` (repaints straight through it), but was disrupting `GlobalPlayer`'s embedded SoundCloud iframe audio on every navigation. Fixed globally: `::view-transition-old(sinteza-bg|global-player), ::view-transition-new(...)  { animation: none; mix-blend-mode: normal; }`. **Any future `transition:persist`'d element embedding real media should get the same treatment.**

## Sandbox/environment notes (for whoever's testing this next in a similarly constrained environment)

- SoundCloud (`w.soundcloud.com`), Google Drive, and plain Google domains are blocked by egress policy in Claude Code's sandboxed sessions — real playback/seeking against the live widget can't be tested there, only simulated via manually-dispatched `player:transport` CustomEvents + rendered-output diffing. `api.github.com` (the plain REST `contents` endpoint `scripts/federate.ts` uses for `listDevlogs`, and the git-trees endpoint `federateCustomPage` uses to list a project's `page/` bundle) also 403s there even though `raw.githubusercontent.com` and normal git push/fetch work fine — federate.ts works correctly in real CI, this is sandbox-only.
- The federated content directories (`src/content/projects/`, `src/content/devlogs/`, `src/generated/projects/`, `public/generated/projects/`) are gitignored and regenerated by `npm run federate` — if testing locally in a sandbox where that fails (see above), it's safe to manually drop real content into those dirs for a local `astro dev`/`astro build` test (mirroring what `federate.ts` would have written — see the mouthpiece migration commit for exactly which files went where), just don't commit them. Real end-to-end verification of a `page/` bundle (real component code, real assets, real interactivity) is possible this way even though the *fetching* step itself can't run in this sandbox — used to verify the mouthpiece migration, including actually decoding and playing its real `.opus` corpus clips headless via Playwright.
